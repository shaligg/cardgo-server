# 卡牌休闲游戏总设计文档

## 1. 文档定位

本文档是项目的产品与玩法总纲，只负责回答：

- 游戏是什么，面向什么玩家。
- 核心体验和长期体验是什么。
- 项目包含哪些系统，各系统解决什么问题。
- 版本推进遵循哪些产品原则。

本文档不维护以下内容：

- 单张卡牌、单个订单、单个关卡或单个活动的具体规则和数值。
- 配置字段、数据表、接口签名、协议号和代码目录。
- 开发任务状态、测试记录和运维流程。

上述内容分别由功能策划文档、后端技术架构文档、`docs/tasks/` 技术任务文档和运维文档维护。

## 2. 项目概述

### 2.1 游戏定位

本项目是一款轻策略、短局制、收集养成型卡牌休闲游戏。

玩家经营一间主题工坊，通过卡牌生产和转换资源、完成订单，并在局外持续收集卡牌、升级工坊、推进章节和参与轻量活动。

### 2.2 核心体验

核心体验是：

```text
轻松经营 + 卡牌组合 + 连锁生产 + 长期收集
```

游戏不以传统卡牌伤害战斗为核心。卡牌用于生产、转换、复制和交付，关卡目标围绕订单与经营展开。

### 2.3 目标用户

- 喜欢轻度策略、卡牌组合和短局体验的休闲玩家。
- 喜欢收集、养成、装饰和长期目标的玩家。
- 每日游戏时间碎片化，但愿意长期积累的玩家。

### 2.4 体验关键词

```text
短局
连锁
收集
工坊
订单
治愈
轻策略
轻社交
可持续活动
```

## 3. 产品支柱

### 3.1 轻松可进入

玩家首次进入时应快速理解“打出卡牌、生产资源、完成订单”的基本目标。新手阶段不要求理解复杂流派或长期经济。

### 3.2 每局有正反馈

单局需要持续提供可感知的资源增长、订单完成或连锁反馈，让玩家容易理解自己的选择产生了什么结果。

### 3.3 局外有长期目标

每次游玩都应推动至少一项长期进度，例如卡牌成长、工坊成长、章节推进、活动兑换或装饰收集。

### 3.4 内容可以持续生产

新增内容优先复用卡牌、订单、关卡、工坊和活动框架。只有无法通过现有规则表达时，才新增底层系统。

### 3.5 付费不破坏休闲感

商业化服务于效率、装饰、收集和轻度加速，不以破坏主线体验或制造强制卡点为代价。

## 4. 世界观与主题

玩家经营一间由猫咪工匠协作运转的工坊。不同章节可以围绕面包、木工、布艺、魔法、海边餐车和节日主题扩展。

主题设计需要同时支持：

- 清晰的美术识别。
- 可复用的卡牌与订单内容。
- 可扩展的活动包装。
- 不改变核心操作逻辑的内容换新。

## 5. 核心循环

### 5.1 单局循环

```text
进入关卡
  -> 使用卡牌生产或转换资源
  -> 完成订单并形成连锁
  -> 达成关卡目标或失败
  -> 结算局外奖励
```

回合、行动点、抽牌、订单刷新、胜负和失败保底等具体规则统一由对应功能策划文档维护。

### 5.2 局外循环

```text
获得奖励
  -> 收集或升级卡牌
  -> 调整卡组
  -> 升级工坊
  -> 解锁新章节与玩法
  -> 进入下一局
```

### 5.3 长期循环

长期留存由以下内容共同支撑：

- 主线章节与主题内容。
- 卡牌收集和流派构筑。
- 工坊成长与装饰表达。
- 每日、周期和活动目标。
- 好友、公会和聊天构成的轻社交关系。

## 7. 内容与玩法方向

### 7.1 主线内容

主线订单是核心内容载体，用于逐步引入资源类型、卡牌能力、订单组合和工坊成长。

### 7.2 周期玩法

每日委托、无尽订单、规则挑战和主题活动用于提供重复游玩的变化，但不能抢占主线验证阶段的开发资源。

每一种周期玩法开始设计或开发前，必须建立独立功能策划文档，明确入口、规则、奖励、配置和验收标准。

### 7.3 活动

活动用于主题换新、资源回收、卡组引导和玩家回流。活动应优先复用现有系统，并将活动规则、周期、货币、商店、奖励和埋点写入独立活动文档。

活动文档建议放在：

```text
docs/design/events/<event_name>.md
```

### 7.4 轻社交

社交定位是轻量、低压力和可选参与：

- 好友用于关系连接和有限互助。
- 公会用于长期归属和协作入口。
- 聊天用于世界与公会沟通。

社交奖励不能成为核心成长的强制来源，治理和反滥用能力随版本逐步补齐。

## 8. 经济与商业化原则

### 8.1 经济原则

- 核心货币和通用材料保持少而清晰。
- 奖励必须有来源，消耗必须有可理解的价值。
- 活动资源与长期经济隔离，避免单次活动冲击主线。
- 资源调整以配置和数据验证为主，不把具体数值写入总纲。

### 8.2 商业化原则

- 优先装饰、收集、通行证、广告激励和轻度效率提升。
- 不出售破坏核心玩法公平感的决定性能力。
- 具体商品、价格、奖励和投放节奏必须进入独立商业化策划文档。

## 9. 版本范围

当前产品阶段、功能数量、里程碑、可砍项和版本出口只维护在 [MVP 范围与里程碑](mvp_scope.md)。

总纲只保留版本推进顺序：

```text
Prototype
  -> 验证核心单局
MVP
  -> 验证成长与基础留存
Soft Launch
  -> 验证经济、运营和商业化
Launch
  -> 建立可持续内容生产
```

## 10. 核心指标

产品评估重点包括：

- 新手是否快速理解核心操作。
- 单局完成率、失败率和中途退出率。
- 卡牌与流派的使用分布。
- 局外成长是否形成下一局动机。
- 资源产消是否长期稳定。
- 社交和活动是否提高留存但不形成负担。

具体埋点、统计口径和目标值应在对应功能策划文档或数据分析文档中定义。

## 11. 主要风险

- 玩法过多导致核心循环不清晰。
- 卡牌效果复杂度超过休闲用户理解成本。
- 内容生产速度跟不上玩家消耗速度。
- 经济产出过快或成长卡点过强。
- 活动为追求差异而重复建设底层能力。
- 总文档、功能文档和技术文档同时维护同一规则，导致口径漂移。

## 12. 文档边界

| 文档 | 唯一职责 |
|---|---|
| 本文档 | 产品定位、核心循环、系统地图和全局产品原则 |
| `mvp_scope.md` | 当前版本范围、优先级、里程碑和出口标准 |
| `*_design.md` | 单个系统或玩法的完整策划规则、配置和验收标准 |
| `architecture_v2.md` | 项目级后端架构总览 |
| `backend_technical_architecture.md` | 后端模块、协议、接口、数据和关键流程 |
| `architecture_v2_task_breakdown.md` | 已有基础架构落地记录，不再承载新增玩法任务 |
| `docs/ops/*` | 运行、压测、发布和验收记录 |

维护规则：

1. 新玩法或新系统开始前，先创建对应功能策划文档。
2. 具体规则只写在功能策划文档，不复制回总设计。
3. 总设计只在产品定位、核心循环或系统地图变化时更新。
4. 通用技术边界变化才更新后端架构文档；单个玩法的策划细节不写入后端总架构。
5. 新任务只读取总纲、当前版本范围、对应功能文档和必要的技术架构章节，不加载全部策划文档。
