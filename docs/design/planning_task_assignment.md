# 策划任务拆分文档

## 1. 目标

本文档用于把《卡牌休闲游戏总设计文档》拆成可执行的策划任务。

总设计文档负责定义方向和边界，后续细节文档由不同策划岗位继续展开。每份细节文档都需要能支持程序、美术、数值、QA 进入开发和验收。

主文档：

- `docs/design/card_casual_game_design.md`

## 2. 策划岗位分工

### 2.1 主策划

负责整体规则、系统边界、版本优先级和跨系统一致性。

主要产出：

- 卡牌系统设计文档。
- 订单与关卡系统设计文档。
- MVP 范围文档。
- 各系统文档的最终整合和评审。

### 2.2 系统策划

负责背包、资产、工坊、卡组、任务、排行榜等系统规则。

主要产出：

- 背包与资产系统文档。
- 工坊系统文档。
- 每日委托系统文档。
- 排行榜系统文档。
- 社交互助系统文档。

### 2.3 数值策划

负责卡牌数值、订单需求、设施消耗、经济产消、成长曲线。

主要产出：

- 经济系统文档。
- 卡牌数值表。
- 订单奖励表。
- 工坊设施升级表。
- 资源投放与消耗表。

### 2.4 关卡策划

负责主线章节、关卡目标、教学节奏、难度曲线。

主要产出：

- 章节与关卡设计文档。
- 新手前 30 分钟流程文档。
- 主线 30 关配置草案。
- 老板订单设计文档。

### 2.5 活动策划

负责限时活动、活动规则、活动任务、活动商店、活动节奏。

主要产出：

- 活动设计模板。
- 第一个中型活动方案。
- 活动任务与兑换商店配置。
- 活动验收标准。

### 2.6 商业化策划

负责付费结构、广告激励、礼包、月卡、通行证。

主要产出：

- 商业化系统文档。
- 月卡方案。
- 通行证方案。
- 广告激励点位方案。
- 首发礼包配置。

## 3. 第一批细节文档任务

### 3.1 卡牌系统设计文档

负责人：主策划 + 数值策划

建议文件：

- `docs/design/card_system_design.md`

需要包含：

- 卡牌类型。
- 卡牌稀有度。
- 卡牌费用规则。
- 卡牌效果类型。
- 卡牌升级规则。
- 卡牌获取方式。
- 卡组编辑规则。
- 流派设计。
- 前 40 张 MVP 卡牌清单。
- 卡牌配置字段。
- 程序实现边界。

验收标准：

- 程序可以根据文档定义卡牌配置结构。
- 数值可以填写第一版卡牌表。
- QA 可以根据文档验证卡牌生效规则。

优先级：P0

### 3.2 订单与关卡设计文档

负责人：关卡策划 + 主策划

建议文件：

- `docs/design/order_level_design.md`

需要包含：

- 订单类型。
- 订单需求结构。
- 订单奖励结构。
- 章节主题。
- 关卡目标类型。
- 难度曲线。
- 新手教学关设计。
- MVP 30 关草案。
- 老板订单基础规则。
- 关卡配置字段。

验收标准：

- 程序可以根据文档实现关卡配置读取和结算。
- 关卡策划可以产出前 30 关配置。
- QA 可以验证关卡胜负和奖励。

优先级：P0

### 3.3 背包与资产系统文档

负责人：系统策划

建议文件：

- `docs/design/inventory_asset_design.md`

需要包含：

- 货币资产列表。
- 道具类型。
- 卡牌是否作为独立库存处理。
- 道具获得来源。
- 道具消耗入口。
- 资产变更日志。
- 幂等与防重复发奖。
- 后端数据结构。
- 客户端展示规则。

验收标准：

- 程序可以实现资产和背包基础接口。
- 后续卡牌、工坊、活动都能复用资产变更能力。
- QA 可以验证发奖、扣除、重复请求。

优先级：P0

### 3.4 工坊系统设计文档

负责人：系统策划 + 数值策划

建议文件：

- `docs/design/workshop_system_design.md`

需要包含：

- 工坊设施列表。
- 每个设施功能。
- 设施升级消耗。
- 设施解锁条件。
- 装饰系统边界。
- 离线收益规则。
- 工坊界面信息结构。
- 工坊数据结构。

验收标准：

- 程序可以实现设施升级和效果读取。
- 数值可以填写设施升级表。
- 美术可以按设施列表评估资源量。

优先级：P0

### 3.5 经济系统文档

负责人：数值策划

建议文件：

- `docs/design/economy_design.md`

需要包含：

- 资源种类。
- 资源来源。
- 资源消耗。
- 前 7 日资源曲线。
- 卡牌升级消耗。
- 工坊升级消耗。
- 关卡奖励。
- 每日委托奖励。
- 无尽订单奖励。
- 活动币和友情币边界。
- 经济风险与调节手段。

验收标准：

- 可以支撑 MVP 前 7 日体验。
- 资源不会在首日明显短缺或溢出。
- 后端和客户端知道每类资源的用途。

优先级：P0

### 3.6 MVP 范围与里程碑文档

负责人：主策划 + 制作人

建议文件：

- `docs/design/mvp_scope.md`

需要包含：

- MVP 功能清单。
- 不做清单。
- Prototype 范围。
- MVP 范围。
- Soft Launch 范围。
- 每阶段验收指标。
- 风险和可砍项。
- 策划、美术、程序任务边界。

验收标准：

- 团队能据此拆开发任务。
- 每阶段验收条件明确。
- 需求范围不会无限扩张。

优先级：P0

## 6. 文档输出规范

每份细节文档至少包含：

- 系统目标。
- 玩家体验。
- 入口和解锁条件。
- 规则说明。
- 配置字段。
- 数据结构。
- 前后端边界。
- 异常处理。
- 数值表或配置样例。
- 验收标准。
- 暂缓内容。

## 8. 评审方式

每份文档完成后建议按以下顺序评审：

1. 策划自查。
2. 制作人评审。
3. 程序评审实现成本。
4. 美术评审资源量。
5. QA 评审验收条件。
6. 数值评审经济影响。

评审通过后再进入开发任务拆分。
